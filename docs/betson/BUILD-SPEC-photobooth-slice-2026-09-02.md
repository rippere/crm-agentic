## Prod-safety summary

Read-only planning session against the LIVE Railway/Supabase CRM — nothing was run, migrated, or deployed. Ordered safest-first. DEMO SEED (PR1) has zero prod surface: in-memory fixtures gated behind NEXT_PUBLIC_DEMO_MODE, never touching the DB, in a file the real seed script does not import. B5's migration (024) and B4's migration (025) are each a nullable column (plus, for B4, one JSONB column with a CONSTANT literal default) = no backfill, no table rewrite, no long ACCESS EXCLUSIVE lock (same profile as the shipped 017_deal_next_action.sql); their only lock risk is the disposition and A/B/C CHECK constraints, which on Postgres <15 validate under ACCESS EXCLUSIVE — trivially fast here because every existing row is NULL, but prefer ADD CONSTRAINT ... NOT VALID then VALIDATE CONSTRAINT (confirm the live PG major version first). RLS RECONCILED (prod-migration-safety RED): the plan's blanket 'No RLS lines in any migration' was verified FALSE — 023_outbound_engagement.sql ships ENABLE ROW LEVEL SECURITY + a <table>_policy for every NEW table and 013_force_rls.sql registers each tenant table; RLS is stripped only in the init_docker mirror and applies only to new tables. Corrected: migrations 024 (activity_events) and 025 (contacts) are COLUMN adds on already-policied tables, and B4's SLA config is COMMITTED to a column on the tenant-root workspaces (verified ABSENT from the 013 tbls array), so no policy lines belong in either migration — and no new unprotected cadence_sla table is introduced. There is NO migration runner in the repo (start.sh only runs uvicorn), so both numbered SQL files are applied to Supabase by hand and mirrored into init_docker.sql (activity_events block line 86 for B5; contacts + workspaces blocks for B4) or Docker drifts. Migration numbering reconciled: B5=024, B4=025 (verified max on disk = 023). B5's server-side mutations ('dead'->Lead.stage='lost' + Contact.status='churned', follow-up->Task insert) must run inside create_activity's single transaction so a failed side effect rolls back the activity. B4's daily cadence sweep only reads contacts and inserts Tasks (no destructive writes) but runs on the live beat, so its breach Task is idempotent via Task.external_id AND the sweep skips NULL-tier / NULL-last_contacted_at contacts to prevent both a cadence_config[None] KeyError and a first-run task storm.

## Decisions locked (2026-09-02, from Ben)

These resolve the blocking open questions above; build to these:

1. **B5 'dead' disposition behavior** → **Churn contact + lose most-recent lead.**
   `Contact.status='churned'` AND set only the **single most recent** matching `Lead.stage='lost'`
   (order by created_at desc, limit 1). Older leads and zero-lead contacts: contact churn only.
2. **B4 `last_contacted_at` maintenance** → **Stamp on call-log write + message fallback.**
   B5's `create_activity` stamps `contacts.last_contacted_at` on a logged call/touch; the cadence
   sweep computes silence as `COALESCE(last_contacted_at, MAX(messages.received_at))`. Contacts with
   neither (never stamped, no messages) are **skipped until first stamp** (no first-sweep storm).
   This makes B4 depend on B5's `events.py` change.
3. **B4 SLA config path** → `workspaces.cadence_config` **JSONB** (default `{"A":15,"B":90,"C":180}`),
   per the reconciled prod-safety fix (no new table, no RLS hole).
4. **Build scope** → build B5 + B4 on the branch, **parked at PRs**, verified (pytest/tsc). **No
   migration is applied to live Supabase without Ben's explicit go.** Postgres major version to be
   confirmed before finalizing the CHECK-constraint apply strategy (plain ADD vs NOT VALID/VALIDATE).
